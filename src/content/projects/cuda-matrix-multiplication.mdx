## Motivation

Matrix multiplication is small enough to understand end to end, but rich enough to expose most of the questions that matter in GPU programming: how threads map to data, which memory hierarchy an access reaches, and whether the kernel is limited by arithmetic or by movement of bytes.

<MarginNote>A useful optimization should come with a model of *why* it helps, not only a faster timing.</MarginNote>

For matrices $A \in \mathbb{R}^{M \times K}$ and $B \in \mathbb{R}^{K \times N}$, the output is

$$
C_{ij} = \sum_{k=0}^{K-1} A_{ik}B_{kj}.
$$

The arithmetic is uncomplicated. The implementation is mostly about arranging those operations so thousands of GPU threads can reuse data efficiently.

## Design

I kept each kernel behind the same host-side interface. That made correctness tests and timing code independent of the implementation being measured.

<Mermaid chart={`flowchart LR

The first kernel assigns one output element to each thread:

```cpp
__global__ void matmul_naive(const float* A, const float* B, float* C,
                             int M, int N, int K) {
    const int col = blockIdx.x * blockDim.x + threadIdx.x;
    const int row = blockIdx.y * blockDim.y + threadIdx.y;

    if (row >= M || col >= N) return;

    float sum = 0.0f;
    for (int k = 0; k < K; ++k) {
        sum += A[row * K + k] * B[k * N + col];
    }
    C[row * N + col] = sum;
}
```

This version is deliberately direct. Neighboring threads read neighboring elements of $B$, but each thread repeatedly fetches values that neighboring threads also need.

## Implementation

The tiled kernel cooperatively loads square regions of $A$ and $B$ into shared memory. Threads synchronize after a load, accumulate partial products, then advance to the next pair of tiles.

<Figure src={`${import.meta.env.BASE_URL}images/tiled-matmul.svg`} alt="Diagram showing two input matrix tiles feeding an output tile" caption="Figure 1. A thread block reuses two input tiles while accumulating one output tile." />

For a tile width $T$, the block performs approximately $2T^3$ floating-point operations after loading $2T^2$ values. Ignoring output traffic, arithmetic intensity therefore grows roughly with tile width:

$$
I \approx \frac{2T^3}{2T^2 \cdot \mathrm{sizeof}(\texttt{float})} = \frac{T}{4}\ \text{FLOP/byte}.
$$

<Callout label="Observation">The equation describes an idealized tile. Boundary checks, occupancy, bank conflicts, and cache behavior still determine whether a larger tile helps on a real GPU.</Callout>
